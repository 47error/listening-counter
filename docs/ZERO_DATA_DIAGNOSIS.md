# 升級後顯示 0：非破壞性診斷

## 結論與證據界線

使用者提供的資訊：v1 JSON 有 21 首歌曲、54 筆紀錄（53 Last.fm、1 手動），歌曲關聯完整。未取得私人備份或原／新網址，因此**尚未確認使用者端根因**，也沒有操作使用者瀏覽器資料。

程式仍讀取 `listening-counter` → `state` → `main`，IndexedDB 實際版本仍為 1；v1→v2 指快照 schemaVersion，沒有建立另一套歌曲表。遷移在記憶體執行，不自動寫回。合成 21／54 v1 快照可完整載入並保留來源、ID、目標、時間、watermarks 與同步游標。平台與期間篩選不隱藏歌曲；取消歌手分類及搜尋後應顯示所有歌曲。遷移驗證失敗原本就會顯示錯誤，不會正常回落成 0。

不同 origin（協定、主機、連接埠）、瀏覽器、Chrome 設定檔或無痕視窗不共用資料。PR 預覽與正式網站的 IndexedDB 不共用。這是無錯誤但 0 首的重要候選原因，仍須實際網址確認。瀏覽器測試以 localhost 與 127.0.0.1 驗證隔離及返回原 origin 的資料保留。

原本 `raw ? migrateState(raw) : emptyState()` 會把 null／false／0 損壞快照誤認為沒有資料，此弱點已修復。但正常 v1 快照是 object，不能將此弱點直接說成使用者本次根因。

## 修復

- readonly transaction 以 key 是否存在判斷新帳本。損壞快照拒絕載入並停止寫入，不清空、不自動修復。
- 新增「本機資料診斷」：目前 origin、資料庫／store／key、IndexedDB／快照版本、未篩選總數；不存在與已存在空快照分開提示。開啟空網站不會自動寫入空快照。
- 寫入前在同一 transaction 比對預期快照與最新資料，不同即中止，避免過期空狀態蓋掉資料。多頁同步使用最新成功提交的快照。
- 備份還原改為「安全補入」。先驗證及預覽，只補缺少的平台、歌曲與事件；保留現有目標、手動事件及已刪除忽略鍵。ID／內容衝突整批停止，不會部分寫入或取代陣列。相同備份重匯不累加。
- 確認補入時重新以最新快照規劃，再經資料庫比對才提交，避免預覽過期。

同 ID 但內容不同時不自動選邊，需保存兩份備份後個別核對。不按歌名去重手動事件。沒有執行 IndexedDB 刪除或 clear；既有使用者主動刪除歌曲／單筆操作仍保留。

## 安全操作

1. 不清除網站資料、不解除安裝瀏覽器，保留原 21／54 備份。不要使用舊版「確認取代並還原」。
2. 比較升級前後完整網址，回原網址、原 Chrome 設定檔查看。若還有資料，先下載備份。
3. 新版診斷若未篩選總數為 21／54，繼續查分類／搜尋；若 0／0，核對是不存快照或已有空快照。不能單憑畫面判定原資料已清除。
4. 選 v1 JSON 檢查安全補入預覽。空帳本應新增 21 首／54 筆；已有資料只補缺少項目，衝突停止。先下載目前備份，再由使用者自行確認補入。
5. 再次選同檔應新增 0／0，重新整理核對 53 Last.fm／1 手動及來源未確認平台。
6. 若格式拒絕，保留原檔，不自行刪欄位或改 ID。需針對實際欄位進一步診斷，不能只憑筆數放寬驗證。
